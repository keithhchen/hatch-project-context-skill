# Hatch 的产品楔子与验证标准

## 课程与咨询之间的产品层

课程能够规模化，但通常过于标准化；咨询能够个性化，但通常过于非标，并受限于本人时间。Hatch 的楔子是在两者之间增加一个新的产品层：用户可以付费使用 Creator 的方法完成一项边界清楚的工作，而不需要买走底层方法，也不要求 Creator 亲自完成每一次交付。

一次性购买和订阅都可以成立。关键不是收费周期，而是 Creator 的方法能否被包装为用户愿意购买、能够重复交付的产品。

## 为什么不能只卖 Skill

Skill 或 Prompt 文件通常存在四个问题：

1. 方法容易被复制、盗版或低价化；
2. 用户安装和配置门槛高；
3. 只有 SOP 或 taste，缺少数据、Tools、Eval 和运行环境；
4. 难以形成完整的支付、分发和持续履约体验。

Hatch 必须补齐：

- 方法保护；
- 支付与商业关系；
- 低摩擦使用体验；
- 真正完成工作的运行能力；
- 数据、Tools、Eval 和持续更新。

## 早期验证看什么

最重要的里程碑不是功能数量，也不是平台叙事完整，而是 Creator 从课程、Skill、数据或方法的衍生产品中获得真实收入。

早期可以采用透明的人工辅助或 concierge delivery 来验证需求，但不能把人工服务冒充已经自动化的 Hatch 产品，也不能用 mock 订单或 fixture 结果证明市场成立。

更可信的验证信号包括：

- Creator 是否愿意向自己的受众分发；
- 是否出现真实付费订单；
- 用户是否接受最终交付物；
- Creator 需要修改多少；
- 每单节省多少 Creator 时间；
- 是否复购；
- 扣除模型、支付和人工升级后的真实毛利。

## 渠道价值

Hatch 不应只逐个寻找 Creator，也应寻找已经与一批成熟 Creator 建立信任的渠道、机构和内容/IP 持有者。对早期 Hatch 而言，Creator portfolio、分发能力和产业信用可能比单纯资金更稀缺。
